
# Microsoft Entra ID - Security & Governance Rules Cheat Sheet

This document outlines key architecture and compliance rules within Microsoft Entra ID (formerly Azure AD) regarding **Self-Operations/Approvals**, **Nested Groups Behavior**, and **Object Scope Restrictions**.

---

## 1. Self-Operations & Approval Restrictions (Rules of "Self")

| Feature / Domain | Rule / Behavior | Exam Key Takeaway |
| :--- | :--- | :--- |
| **Access Reviews** | **Allowed by default** | Users and Group Owners can review their own access unless the option **"Prevent users from reviewing their own access"** is explicitly enabled in the settings. |
| **Access Reviews (Fallback)** | **Required when no owners exist** | Fallback reviewers are triggered *only* if the target group/resource has no assigned active owners. |
| **PIM (Self-Activation)** | **Allowed** | Users can activate eligible roles assigned to themselves. |
| **PIM (Self-Approval)** | **Forbidden** | If User A requests a role activation and User A is listed as an approver, User A **cannot** approve their own request. Approval requires a distinct user/group. |
| **Administrative Units (AUs)** | **No Self-Elevation** | An AU Administrator cannot add themselves to Global Admin roles or expand their own AU scope beyond delegated boundaries. |
| **User & Admin Consent** | **Owner Consent Limits** | An App Owner cannot grant tenant-wide consent to their own enterprise application without Global Admin / Privileged Role Admin roles. |

---

## 2. Nested Groups Behavior & Technical Constraints


```

NESTED GROUPS (Groups Inside Groups)
│
├── Access Reviews ─────────► AUTOMATICALLY FLATTENED (Includes direct & indirect users)
│                             └── CRITICAL: Denying a nested user does NOT remove them
│                                 from the child group automatically.
│
├── Group-Based Licensing ──► NOT SUPPORTED (Only DIRECT group members receive licenses)
│
├── Role-Assignable Groups ─► BANNED (isAssignableToRole = true groups CANNOT contain
│                             or be inside nested groups)
│
├── Dynamic Groups ─────────► NOT SUPPORTED (Cannot contain other groups as members)
│
└── Conditional Access ─────► SUPPORTED (Nested group memberships are evaluated)

```

### Detailed Breakdown:
* **Access Reviews (Identity Governance):** 
  * Nested groups are **automatically flattened**. The review scope evaluates all individual user accounts inside nested groups.
  * *Removal Limitation:* If a reviewer selects **Deny** for a nested user, Entra ID **cannot automatically remove** the user from the nested group. Manual intervention or Lifecycle Workflows are required.
* **Group-Based Licensing:**
  * **Not supported.** License inheritance applies **strictly to direct members**. Users inside nested groups will fail to acquire the license.
* **Role-Assignable Groups (`isAssignableToRole = true`):**
  * **Nesting is completely blocked.** Role-assignable groups cannot contain nested groups, nor can they be nested inside other groups.
* **Dynamic Groups:**
  * Cannot contain other groups. Membership rules evaluate user or device attributes only.

## 3. Scope & Object Target Rules

| Target Scope | Included Objects | Excluded Objects / Limitations |
| :--- | :--- | :--- |
| **"All Users" (Access Reviews)** | Human User Objects (`UserType == Member` or `Guest`) | **Managed Identities** & **Service Principals** are excluded (requires Workload Identity Reviews). |
| **Enterprise Application Assignment** | Security-Enabled Groups (**Security Groups**, **Mail-Enabled Security Groups**) | **Distribution Groups** and standard **M365 Groups** (without security flags) cannot be assigned. |
| **Administrative Units (AUs)** | Users, Groups, Devices | AUs **cannot be nested** inside other AUs. |

## Quick Memory Rules for SC-300 Exam

1. **Access Review + Self-Review:** *Allowed by default* (can be toggled off in settings).
2. **Access Review + Nested Group + Deny:** *Denying access does NOT remove the user from the nested group*.
3. **PIM + Self-Approval:** *NEVER allowed* (Requesters cannot approve their own requests).
4. **Licensing + Nested Groups:** *NEVER inherited* (Direct members only).
5. **Role-Assignable Groups:** *Zero nesting allowed* (Must be flat).
6. **"All Users" Scope:** *Refers exclusively to human user accounts* (Excludes Managed Identities).

### 1. Ownership Rules (App Registration vs. Enterprise Application)

| Entity | Allowed Owners | Disallowed Owners (Exam Traps) |
| --- | --- | --- |
| **App Registration** *(Global Blueprint)* | • **Users** (Internal or Guest)<br>

<br>• **Service Principals** (e.g., Managed Identities, automation apps) | • **Groups** (Security or M365 groups **cannot** own an App Registration) |
| **Enterprise Application** *(Local Service Principal)* | • **Users ONLY** (Internal or Guest) | • **Service Principals** (cannot own an Enterprise App)<br>

<br>• **Groups** (cannot own an Enterprise App) |

> **Exam Trap — "Owner" vs. "User Assignment":**
> Being assigned as an **Owner** of an Enterprise Application allows you to *manage* its settings (SSO, certificates, user assignments), **NOT** to sign in and use the app if *Assignment required?* is set to **Yes**. To use the app, the owner must also be explicitly added under **Users and groups**.

---

### 2. Assignment Rules (Who Can Be Assigned to an Enterprise Application?)

Assignments happen on the **Enterprise Application** (*Users and groups*), while **App Roles** are defined on the **App Registration** (`Allowed member types`).

| Principal / Group Type | Can be Assigned to Enterprise App? | Notes & SC-300 Exam Traps |
| --- | --- | --- |
| **Users** (Members & B2B Guests) | **Yes** (Entra ID Free) | Works with any license tier. |
| **Security Groups** (Assigned or Dynamic User) | **Yes** (**Requires Entra ID P1/P2**) | **Direct members only.** Nested groups are **NOT** supported! |
| **Mail-Enabled Security Groups** | **Yes** (**Requires Entra ID P1/P2**) | Supported because `securityEnabled = true`. |
| **Microsoft 365 Groups** | **Conditional** (`securityEnabled = true`) | M365 groups created via Entra/Teams have `securityEnabled = true` by default and work. Legacy/non-security M365 groups (`securityEnabled = false`) **cannot** be assigned. |
| **Distribution Groups** | **No** | Never supported for app access or role assignment (`securityEnabled = false`). |
| **Service Principals** (Other Apps / Managed IDs) | **Yes** *(via Graph/PowerShell or API Consent)* | Requires the App Role's `Allowed member types` to be set to **Applications** or **Both**. **Cannot** be picked from the portal's standard *Users and groups* UI. |

---

### 3. Quick SC-300 Exam Memory Anchors

* **Ownership:**
* App Registration = **Users + Service Principals** (No Groups).
* Enterprise App = **Users ONLY** (No Service Principals, No Groups).


* **Group Assignment License Trap:** Assigning **individual users** = **Free**. Assigning **groups** = **Entra ID P1/P2 required**.
* **Group Flattening Trap:** If `Group B` is nested inside `Group A`, and `Group A` is assigned to the Enterprise App $\rightarrow$ **`Group B` users get NO access and NO app role claims**.
* **Security Flag Rule:** Any group assigned to an Enterprise App **must** have `securityEnabled = true` (Security groups, Mail-enabled security groups, and standard M365 groups). Distribution lists are always excluded.
* **App Role `Allowed member types`:**
* `Users/Groups` $\rightarrow$ Human identities & security-enabled groups.
* `Applications` $\rightarrow$ Service principals / daemon apps (OAuth 2.0 `client_credentials` flow).
* `Both` $\rightarrow$ Users, groups, and service principals.



## Understanding the Difference: Ownership vs Assignment vs App Role Assignment

Many SC-300 questions become confusing because **Ownership**, **Application Assignment**, and **App Role Assignment** are different concepts with different supported principals.

### 1. Ownership (Who Can Manage the Object?)

Owners can manage the object's configuration.

| Object | Users | Groups | Service Principals |
| --- | --- | --- | --- |
| **App Registration** | ✅ Yes | ❌ No | ✅ Yes |
| **Enterprise Application (Service Principal)** | ✅ Yes | ❌ No | ✅ Yes |

**Key Exam Rule:**

> Only **Users** and **Service Principals** can be owners. Groups can never be owners.

---

### 2. Enterprise Application Assignment (Who Can Access the Application?)

Assignments are configured under:

**Enterprise Application → Users and Groups**

| Principal Type | Can be Assigned? |
| --- | --- |
| Users | ✅ Yes |
| Security Groups | ✅ Yes (P1 required) |
| Mail-Enabled Security Groups | ✅ Yes (P1 required) |
| Microsoft 365 Groups | ✅ Yes (security-enabled) |
| Distribution Groups | ❌ No |
| Service Principals | ❌ No |

**Purpose:**

Controls whether a principal can sign in to and access the application.

**Example:**

* User **Alice** assigned → can access Salesforce.
* Security Group **Sales Team** assigned → all direct group members can access Salesforce.
* Service Principal **ReportingApp** cannot be assigned through *Users and Groups*.

---

### 3. App Role Assignment (Who Receives an Application Role?)

App roles are defined in:

**App Registration → App Roles**

and assigned on the:

**Enterprise Application**

| Principal Type | Can Receive App Roles? |
| --- | --- |
| Users | ✅ Yes |
| Security-Enabled Groups | ✅ Yes |
| Service Principals | ✅ Yes (if `AllowedMemberTypes` includes `Applications`) |
| Distribution Groups | ❌ No |

**Purpose:**

Controls which role appears in the token (`roles` claim).

**Example:**

App Role = `Admin`

* Alice → receives `Admin`
* Sales Team group → members receive `Admin`
* ReportingApp service principal → receives `Admin` only if the role allows `Applications`

---

Think of the objects like this:
