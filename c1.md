
# Microsoft Entra ID - Security & Governance Rules Cheat Sheet

This document outlines key architecture and compliance rules within Microsoft Entra ID (formerly Azure AD) regarding **Self-Operations/Approvals**, **Nested Groups Behavior**, and **Object Scope Restrictions**.

---

## 1. Self-Operations & Approval Restrictions (Rules of "Self")

| Feature / Domain | Rule / Behavior | Exam Key Takeaway |
| :--- | :--- | :--- |
| **Access Reviews** | **Allowed by default** | Users and Group Owners can review their own access unless the option **"Prevent users from reviewing their own access"** is explicitly enabled in the settings. |
| **Access Reviews (Fallback)** | **Required when no owners exist** | Fallback reviewers are triggered *only* if the target group/resource has no assigned active owners. |
| **PIM (Self-Activation)** | **Allowed** | Users can activate eligible roles assigned to themselves. |
| **PIM (Self-Approval)** | **Forbidden** | If User A requests a role activation and User A is listed as an approver, User A **cannot** approve their own request. Approval requires a distinct user/group. |
| **Administrative Units (AUs)** | **No Self-Elevation** | An AU Administrator cannot add themselves to Global Admin roles or expand their own AU scope beyond delegated boundaries. |
| **User & Admin Consent** | **Owner Consent Limits** | An App Owner cannot grant tenant-wide consent to their own enterprise application without Global Admin / Privileged Role Admin roles. |

## 2. Nested Groups Behavior & Technical Constraints


```

NESTED GROUPS (Groups Inside Groups)
│
├── Access Reviews ─────────► AUTOMATICALLY FLATTENED (Includes direct & indirect users)
│                             └── CRITICAL: Denying a nested user does NOT remove them
│                                 from the child group automatically.
│
├── Group-Based Licensing ──► NOT SUPPORTED (Only DIRECT group members receive licenses)
│
├── Role-Assignable Groups ─► BANNED (isAssignableToRole = true groups CANNOT contain
│                             or be inside nested groups)
│
├── Dynamic Groups ─────────► NOT SUPPORTED (Cannot contain other groups as members)
│
└── Conditional Access ─────► SUPPORTED (Nested group memberships are evaluated)

```

### Detailed Breakdown:
* **Access Reviews (Identity Governance):** 
  * Nested groups are **automatically flattened**. The review scope evaluates all individual user accounts inside nested groups.
  * *Removal Limitation:* If a reviewer selects **Deny** for a nested user, Entra ID **cannot automatically remove** the user from the nested group. Manual intervention or Lifecycle Workflows are required.
* **Group-Based Licensing:**
  * **Not supported.** License inheritance applies **strictly to direct members**. Users inside nested groups will fail to acquire the license.
* **Role-Assignable Groups (`isAssignableToRole = true`):**
  * **Nesting is completely blocked.** Role-assignable groups cannot contain nested groups, nor can they be nested inside other groups.
* **Dynamic Groups:**
  * Cannot contain other groups. Membership rules evaluate user or device attributes only.

## 3. Scope & Object Target Rules

| Target Scope | Included Objects | Excluded Objects / Limitations |
| :--- | :--- | :--- |
| **"All Users" (Access Reviews)** | Human User Objects (`UserType == Member` or `Guest`) | **Managed Identities** & **Service Principals** are excluded (requires Workload Identity Reviews). |
| **Enterprise Application Assignment** | Security-Enabled Groups (**Security Groups**, **Mail-Enabled Security Groups**) | **Distribution Groups** and standard **M365 Groups** (without security flags) cannot be assigned. |
| **Administrative Units (AUs)** | Users, Groups, Devices | AUs **cannot be nested** inside other AUs. |

---

## Quick Memory Rules for SC-300 Exam

1. **Access Review + Self-Review:** *Allowed by default* (can be toggled off in settings).
2. **Access Review + Nested Group + Deny:** *Denying access does NOT remove the user from the nested group*.
3. **PIM + Self-Approval:** *NEVER allowed* (Requesters cannot approve their own requests).
4. **Licensing + Nested Groups:** *NEVER inherited* (Direct members only).
5. **Role-Assignable Groups:** *Zero nesting allowed* (Must be flat).
6. **"All Users" Scope:** *Refers exclusively to human user accounts* (Excludes Managed Identities).

```
SELF-OPERATIONS & APPROVALS
│
├── Access Reviews
│   ├── Self-Review: ALLOWED by default (Users/Owners can review themselves).
│   ├── Block Self-Review: Can be explicitly disabled in settings ("Prevent users from reviewing their own access").
│   └── Fallback Reviewers: Required when a group/resource has NO active owners.
│
├── Privileged Identity Management (PIM)
│   ├── Self-Activation: ALLOWED (Users can activate their eligible roles).
│   ├── Self-Approval: FORBIDDEN.
│   │   └── If User A requests Role X and User A is an Approver → User A CANNOT approve their own request.
│   ├── Approval Assignment: Requires a distinct designated user/group (excluding the requester).
│   └── Access Reviews in PIM: Self-review allowed unless blocked by admin setting.
│
├── Administrative Units (AUs)
│   ├── Scope Limit: An AU Admin CANNOT manage objects outside their AU.
│   └── Self-Elevation: An AU Admin CANNOT add themselves to a Global Admin role or expand their own AU scope.
│
└── User Consent & App Registration
    ├── Self-Consent: Allowed ONLY for low-impact permissions if User Consent is enabled.
    ├── Admin Consent: Required for high-privilege scopes (Graph API read/write all, etc.).
    └── App Ownership: An App Owner CANNOT grant tenant-wide consent to their own app (requires Global Admin / Privileged Role Admin).

NESTED GROUPS (Groups inside Groups)
│
├── Access Reviews (Identity Governance)
│   ├── Behavior: AUTOMATICALLY FLATTENED.
│   ├── Scope: Review includes direct members AND nested members (all user objects).
│   └── REMOVAL LIMITATION (CRITICAL):
│       └── If a nested user is DENIED in a review, Entra ID CANNOT automatically 
│           remove them from the nested group. (Requires manual intervention or Lifecycle Workflows).
│
├── Group-Based Licensing
│   ├── Behavior: NOT SUPPORTED for nested groups.
│   └── Rule: Licenses are inherited ONLY by DIRECT members of the assigned group. 
│             Users in nested groups will NOT receive the license.
│
├── Conditional Access & Security Group Assignments
│   ├── CA Policies: SUPPORTED (nested groups are evaluated).
│   └── Enterprise App Assignments: SUPPORTED for authentication, but NOT recommended 
│       for automated SCIM provisioning.
│
├── Role-Assignable Groups (PIM & Entra Roles)
│   ├── Rule: NESTED GROUPS ARE BANNED.
│   └── Requirement: A group with `isAssignableToRole = true` CANNOT contain nested groups 
│                    and CANNOT be nested inside another group.
│
└── Dynamic Groups
    └── Rule: CANNOT contain other groups (nested rules like `user.memberOf` are not supported).

SCOPE & OBJECT TARGETING
│
├── Access Reviews Scopes
│   ├── "All Users": Includes human User objects ONLY.
│   │   └── EXCLUDES: Managed Identities (Service Principals) & Guest Users (unless selected).
│   ├── "Guest Users": Targets `UserType == Guest` only.
│   └── Service Principals: Reviewed via distinct Workload Identity Reviews (not "All Users").
│
├── Enterprise Application Group Assignments
│   ├── Valid Group Types (Must be Security-Enabled):
│   │   ├── Security Groups (Cloud-only or Synced AD) → YES
│   │   └── Mail-Enabled Security Groups → YES
│   └── Invalid Group Types:
│       ├── Distribution Groups → NO
│       └── Standard M365 Groups (without security flag) → NO
│
└── Administrative Units (AU) Membership
    ├── Valid Objects: Users, Groups, Devices.
    └── Exclusion: You CANNOT place an AU inside another AU (No nested AUs).
```
